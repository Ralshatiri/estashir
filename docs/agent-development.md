# كيف نبني النظام الوكيلي؟

## المرحلة الحالية

الواجهة مرتبطة الآن بـ backend/server.py. يبدأ كل حوار بجلسة ADK عشوائية،
وتصل الرسائل إلى Runner ثم Gemini. يعيد API نص الرد وبيانات الأدوات، وتحدّث
React الواجهة منها. أزلنا determineTriage والتسلسل الثابت من المحادثة التفاعلية.
الصوت الخام يمر عبر WebSocket إلى Runner.run_live() ونموذج gemini-3.8-live،
ويعود صوت النموذج ونصه المصاحب. لا يوجد تعرف صوتي أو توليد كلام بواسطة المتصفح.

## ما الفرق بين النموذج وADK والوكيل؟

Gemini هو النموذج الذي يفهم الحوار ويولد الإجابات. ADK هو إطار التشغيل الذي
يوصل الرسائل بالنموذج ويتيح استدعاء الأدوات ويتابع أحداث الجلسة. الوكيل هو
تعريف يجمع النموذج وتعليماته والأدوات المسموح له باستخدامها.

بدأنا بوكيل واحد لأن جمع المعلومات والتوجيه محادثة واحدة ذات سياق مشترك.
لا تضيف عدة وكلاء قيمة تلقائية، ويمكن فصل المسؤوليات لاحقًا إذا ظهر احتياج واضح.

## دورة التنفيذ

1. تصل رسالة المريض إلى جلسة ADK.
2. يقرأ النموذج التعليمات وسياق المحادثة ونتائج الأدوات السابقة.
3. يقرر أن يسأل سؤالًا أو يستدعي أداة.
4. تنفذ ADK الدالة في Python؛ الدالة تحفظ بيانات الجلسة وتعيد نتيجة منظمة.
5. يرى النموذج نتيجة التنفيذ، ثم يجيب أو يواصل جمع المعلومات.

instructions.md يحدد السلوك ولا يدرّب النموذج. تغييره يغيّر تعليمات التشغيل.
agent.py يسجل الأدوات؛ لا تعطي التعليمات وحدها صلاحية تنفيذ وظيفة غير موجودة.

## الأدوات والحالة

- get_intake يقرأ البيانات التي سجلتها أدوات الجلسة.
- record_consent يسجل الموافقة الصريحة أو الرفض. عند سحب الموافقة يمسح بيانات
  intake الحالية؛ هذا لا يحذف تاريخ الرسائل والأحداث السابق في ADK.
- record_medical_number يحفظ الرقم دون ادعاء التحقق منه في نظام مستشفى.
- record_symptom يحفظ كلام المريض مع النفي والسياق؛ إضافة معلومة تلغي التوجيه
  السابق من حالة intake حتى يعيد الوكيل تقييمه.
- submit_routing يحفظ المسار الذي اختاره النموذج، وسببه وملخصه وعدم اليقين.

التحقق من الموافقة والقيم المقبولة ليس تصنيفًا طبيًا قائمًا على قواعد.
لا توجد في هذه الأدوات قائمة أعراض أو شروط كلمات تحدد المسار.
الأدوات تكتب في جلسة ADK، ثم يعيد API بياناتها للواجهة التي تزامن حالة العرض
الحالية إلى Supabase. الأدوات لا تنفذ حجزًا فعليًا في نظام مستشفى.

## تفاصيل الربط وما تبقى

- agentClient.ts ينشئ الجلسة ويرسل الرسائل عبر Vite proxy. معرّف الجلسة يبقى
  في تبويب المتصفح، ويُجدَّد عند بداية محادثة جديدة.
- server.py يستخدم InMemorySessionService وRunner. يقرأ نتيجة أدوات الجلسة
  ويربطها بحقول DemoState؛ لا يختار مسار الرعاية بنفسه.
- الواجهة تمنع الإرسال المتكرر أثناء الرد وتتجاهل الرد المتأخر بعد إعادة الضبط.
- عند فشل الوكيل لا يوجد بديل قواعدي. يطلب التطبيق بداية حوار جديد؛ الخلفية
  تلغي الجلسة التي فشلت لتجنب تكرار رسالة داخل سجل جزئي.
- تشغيل backend وfrontend مطلوب؛ adk web وحده لا يخدم API التطبيق.
- API محلي فقط: لم نضف تسجيل دخول، ملكية جلسات إنتاجية، تخزينًا دائمًا أو حدود استخدام.
- استمرار مزامنة DemoState إلى صف Supabase المشترك خاص بالعرض الحالي، ويحتاج
  فصل بيانات المرضى وتصميم الموافقة والتخزين قبل الإنتاج.
- أُضيف بث صوتي ثنائي الاتجاه عبر ADK. live_transport.py يحول أحداث الصوت
  والنص والمقاطعة ونهاية الدور إلى رسائل WebSocket، دون تغيير القرار السريري.
- في نماذج Live الحديثة قد يستمر عمل الأدوات بعد نهاية دور صوتي؛ ننتظر حالة
  انتهاء التفاعل قبل تطبيق بيانات التوجيه، ثم ننتظر انتهاء تشغيل الصوت في العميل.
- تقييمات النموذج السريرية وتخزين الجلسات الدائم ما زالا عملًا لاحقًا.

## كيف نتحقق من السلوك؟

نفصل اختبارات الأدوات الحتمية عن تقييمات النموذج غير الحتمية. نفحص رفض حفظ البيانات
دون موافقة، وصحة البيانات، واستقلال الجلسات. ثم نقيم حوارات عربية تشمل النفي،
والمعلومات غير المكتملة، والرفض، وتصحيح الأعراض، والاشتباه بالطوارئ، ومحاولات
تغيير تعليمات المساعد. نجاح البناء لا يثبت جودة التوجيه الطبي؛ الحالات والتوقعات
السريرية تحتاج مراجعة مختص قبل الاستخدام الفعلي.

## إعداد الصوت ومراجعه

ESTASHIR_LIVE_MODEL يضبط نموذج Live؛ ESTASHIR_MODEL يضبط نموذج النص.
المساران يشتركان في create_agent والتعليمات والأدوات، لكنهما يستخدمان جلسات منفصلة.
الميكروفون AudioWorklet ينشئ PCM16 little-endian بتردد16kHz. لا تُرفع تسجيلات
مسبقة ولا يُرسل مفتاح Gemini إلى المتصفح. تدير الخلفية اتصال Live واستدعاء الأدوات.
اختبارات test_live.py تتحقق من نقل PCM والنص والمقاطعة وحالة التفاعل والتنظيف،
باستخدام نموذج وهمي. اختبار النموذج الحقيقي تحقق من عودة صوت ونص عبر run_live؛
هذا لا يغني عن تجربة الميكروفون والسماع في المتصفح أو تقييم جودة التوجيه.
